# 碰撞系統品質驗證（G-01「碰撞品質」）

驗證對象：`apps/simulator` 的三層碰撞——
`core/physicsBackend.ts`（SimpleBackend：AABB 最小穿透軸推出）、
`render/havokBackend.ts`（Havok WASM：`pointProximity` 球對網格推出）、
`multiplayer/soccer.ts`（足球機對機球對球推出）——以及 `core/physics.ts` 的地板 / 天花板 clamp 與它們的交互。
鐵律：不換引擎、不動架構、不改玩法、不改手感常數（THRUST / DRAG / LIFT）；只驗證與修真 bug。

## 方法

- headless Chromium（playwright-core 1.58 + chromium headless shell，`--use-angle=swiftshader --enable-unsafe-swiftshader`）開 vite dev（`?autologin=1&level=1-6` / `?autologin=1&soccer=1`）。
- 測試在頁面內 `import('/src/core/physics.ts')` 等模組（vite dev 同一 URL = 同一模組實例，與 `main.ts` 共用同一份 `droneState`），把 `flags.paused = true` 停掉主迴圈後，**逐 tick 呼叫真實的 `applyManualControls → integrate → resolveObstacleCollisions (→ tickSoccerMatch)`**，順序與 `main.ts fixedTick` 相同。位置 / 速度直接寫 `droneState`。
- 機對機：兩個 headless 客戶端各跑真實 `tickSoccerMatch`，Node 腳本充當假伺服器——每 5 tick（≈80ms，對齊 `POS_SEND_MS`）交換一次位置，分身端照常以 `INTERP=0.25` 內插。
- 量測：每 tick 記錄位置 / 速度；「穿透深度」= 球心落在膨脹 AABB（half + R）內的最小軸深度、以及是否落在**實體方塊內**；門框用解析 torus（球心到管中心線距離 vs `tube_r + BALL_R = 1.07`）；抖動 = 穩定段內位置極差。
- 測試腳本在 scratchpad（不進 repo）；測完已關閉瀏覽器與 dev server。

常數：`DRONE_RADIUS = 0.6`、`SOCCER_BALL_R = 0.8`（門框碰撞半徑）、Havok 撞擊衰減 0.4、機對機 `SOCCER_CONTACT_R = 0.5`（最小間距 1.0）/ 衰減 0.55。
速度上限：`THRUST × DRAG / (1 − DRAG) = 0.012 × 0.92 / 0.08 ≈ 0.138 /tick`；鬼抓人「鬼」×1.5 ≈ 0.207 /tick。測試用 0.15 與 0.21（皆 ≥ 極速）。

## 修正（2 處，各 ≤ 6 行）

1. **`apps/simulator/src/core/physics.ts` `resolveObstacleCollisions()`**：後端推出後加地板 / 天花板護欄（只修位置；不動速度、起降狀態、不播音效）。
   原因：方塊底離地（或頂離天花板）< 球半徑且高速切入時，AABB 最小穿透軸選 y、把球心推到地板下 / 天花板上，下一 tick `integrate` 的 clamp 再拉回來 → 每 tick 打架，且 `integrate` 的 `p.y < 0.4` 分支把飛行中的機身誤判「落地」（6e：y 0.3↔0.4、isFlying→false；3d：y 30.1↔30）。
   影響範圍：現有關卡 / 大亂鬥掩體 / 足球假人的方塊底最低 1.75（大亂鬥掩體）、頂最高 7.25，遠離護欄區間 → 現有內容行為零改變；G-04 確定性回放 hash 不變（已跑 `verify:determinism` 全過）。
2. **`apps/simulator/src/multiplayer/soccer.ts` `resolveDroneContacts()`**：完全重疊（d < 1e-6）的退化方向從「兩邊都 +x」改為「playerId 字典序小的 −x、大的 +x」。
   原因：進場時所有人都站中場 (0,0.4,0)（收到 spawns 前 / 中途加入者），兩客戶端各算出 +x → 同步位移、永遠重疊、一路互推到邊牆（5a）。兩端方向相反後 1 tick 分開。

## 為什麼不需要掃描（sweep）/ 子步進（substep）

- AABB：單 tick 最大位移 0.138（鬼 0.207）≪ 球半徑 0.6，更 ≪ 膨脹方塊厚度（≥ 2×(1+0.6)=3.2）；每 tick 都在「離面 ≤ 位移」的位置被推回面上，球心永遠在正確側，數學上不可能跳過整個方塊（1a–1e、6d 實測 0 穿透）。
- Havok 網格：`pointProximity(maxDistance = radius)` 是**距離查詢不是射線**，接觸後球心距面 ≥ radius，下一 tick 最多再進 0.207 < 0.8，永遠在同一側被推回；門框管徑 0.54 也大於單 tick 位移。實測 30+ tick 最大穿透 0.0005（= 網格離散誤差）。
- 因此維持每 tick 一次解算，不加子步（加了只會多花 CPU、不改結果）。若未來手感常數或 `GHOST_SPEED` 讓極速 ≥ 球半徑（≈ 0.6/tick，現值的 3–4 倍），才需要回頭做子步。

## 已知限制（誠實記錄）

- **機對機是 client 權威 + 網路延遲**：兩機對衝時「真」距離會短暫低於最小間距（5d 最低 0.34；12.5Hz 上報 + 0.25 內插 ≈ 4–6 tick 延遲）；但每個客戶端畫面上自己與分身的距離始終 ≥ 1.0，學生看不到互穿。同向追撞會有 ≈0.3 秒週期的「頂—退—再追」節奏（5f），是接觸衰減 0.55 的自然結果，不是抖動。
- **AABB 最小軸語意**：擦邊角時會被「側推」一小段（1c：0.1）而不是滑面切線推開；與 legacy 相同、學生不易察覺。
- **護欄下的視覺**：方塊底 0.85–1.0 之間（現有內容沒有）貼地極速滑入時，機身會被地板護欄留在 y=0.4、球體與方塊底重疊 ≤ 0.1（碰撞球本就「略大於機身」）——不再下沉 / 誤落地，但仍會從方塊下滑過去，屬資料設計問題（關卡作者不該把實心方塊底放在離地 < 1.0）。
- **程式模式**（Blockly tween 直接寫位置）：碰撞每 tick 只推一次，tween 下一 tick 又把位置寫回更深處，最終會從方塊另一側推出（等同 legacy），不在本次範圍。
- **playground glb**（大亂鬥）的網格碰撞未在本輪覆蓋（需 arena 伺服器 + 場地切換）；同一 `HavokBackend` 路徑已由門框情境驗證。若 glb 含地面三角形，球半徑 0.6 會讓落地高度停在 0.6 而非 0.4（legacy 相同）——待 arena QA 時確認。
- **swiftshader**：headless 下 Havok WASM 行為與實機一致（純 CPU、與 GPU 無關），僅渲染幀率不同；本測試逐 tick 呼叫、不受幀率影響。
